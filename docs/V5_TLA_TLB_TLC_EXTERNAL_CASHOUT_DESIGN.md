# TimeLink V5 — TL_A / TL_B → TLC → 외부 거래소 정책 및 구현 계약

상태: **설계 확정 후보 / 실제 환전·전송 기능 미활성화**. 2026-10-23 논의 기준. 기존 채굴·재생·정산 기능을 변경하지 않는다.

## 사용자 의도와 자산 경계
- TL_P: 구매로 취득한 TL. 사용 시 TL_B로 전환되는 정책을 V5 경제원장과 정합성 검증 후 구현한다. 기존 70% 창작자 / 30% 플랫폼 재생 정산은 보존한다.
- TL_A: 광고 보상. TL_B: 청취·활동·기여 보상 및 정책상 전환분. **TL_A/TL_B 자체를 플랫폼이 원화로 직접 환전해 주지 않는다.**
- 이용자는 POC 기여 검증을 거쳐 TLC를 획득하고, 실제 TON 네트워크의 검증된 TLC Jetton을 자신의 TON 지갑으로 출금한 뒤, **실제로 TLC 입금·거래를 지원하는 외부 거래소가 존재하는 경우에만** 그 거래소에서 스스로 매도한다. 거래소 상장, 매수 유동성, 원화 지급 및 가격은 보장하지 않는다.
- V5 원장 내 TL, 내부 채굴 표시 TLC, TON 온체인 TLC는 별도 잔액과 상태로 취급한다. 내부 잔액만으로 온체인 출금 가능하다고 표시하지 않는다.
- **공식 발행/환전 정책:** TimeLink가 직접 운영하는 공식 전환은 TL → TLC 단방향이며 TLC를 회수해 신규 TL을 발행하거나 회사 자금으로 역환전하지 않는다. **별도 P2P Exchange Pool은 양방향 거래 허용:** 사용자끼리 기존 보유 TL과 TLC를 맞교환하며 TimeLink는 에스크로·수수료 중개만 한다. TLC를 주고 TL을 받는 P2P 거래는 신규 TL 발행이 아니다.

## 가장 먼저 확정할 경제 정책
1. **소각형**: TL_A/TL_B 잔액을 차감하고 정해진 전환식으로 TLC 발행, 또는 **기여채굴형**: TL_A/TL_B의 검증된 사용·기여 이력을 근거로 TLC를 추가 채굴. 두 방식을 동시에 적용하여 동일 보상을 중복 발행하지 않는다.
2. 기존 `src/economics.ts`의 TLC 채굴식: `(월 TL_P 소비/30) × 0.08 × POC지수 × 플랜배율`, 일별 `min(계산량, 월소비×0.30/30)`. 기존 공식은 TL_A/TL_B 소각 전환을 구현하지 않는다. 전환율, 소각 여부, TL_A/TL_B의 POC 기여계수는 관리자가 명시적으로 승인할 때까지 미정이다.
3. 관리자가 정하는 **TL → TLC 단방향 전환율**은 미확정이며, 회사가 TLC를 매입해 TL을 새로 지급하는 역방향 공식 환전 기능은 만들지 않는다. P2P 주문 호가는 이용자 간 자유롭게 결정한다. 외부 TLC 시장가격은 별개이고 플랫폼은 이를 보장하지 않는다.
4. **TLC ↔ TL P2P 에스크로는 양방향 허용한다.** 양측 기존 잔액을 잠근 후 소유권 이전만 실행한다. 회사가 매수 상대방이 되거나 TLC를 회수하고 신규 TL을 발행하지 않는다. 단방향 전환율, 채굴 계수, 한도는 관리자 수동 조정·승인·감사 이력을 갖춘다.

## 구현 단계와 안전 조건
### 1단계: V5 원장 및 채굴 실태 감사
- `src/economics.ts` 레거시 `users.tlc_balance`와 V5 `v3_economy_accounts` TLC 잔액의 관계, `/api/eco/mine-tlc` 경로, 프런트 호출 경로, TL_P→TL_B 사용 시점, 월 하드캡 실제 동작 검증.
- 보상 출처, 채굴 근거 이벤트 ID, 채굴/전환 정책 버전, 환산율, 발행 총량, 환전 적격 여부를 별도 기록.
- TL_A/TL_B 사용·차감과 POC 채굴 사이 이중 보상·재진입 방지. 잔액 음수 금지, idempotency, 원장 대차 일치.

### 2단계: 통합 지갑
- TL_P/TL_A/TL_B/환전 적격 TL과 TLC(내부·온체인 구분) 표시.
- TON Connect 서명으로 지갑 소유권 확인. 사용자 개인키·시드문구를 서버에 저장하지 않는다.
- 공식 TLC Jetton master 주소와 decimals, 출금 수수료·네트워크 비용, TON 지갑 주소 형식을 검증. 검증되지 않은 자산은 입출금 차단.

### 3단계: TLC 출금
- 사용자 요청 → 보유 TLC 예약/잠금 → 온체인 서명·전송 → 블록 확정 검증 → 원장 완료. 실패·타임아웃은 중복 지급 없이 재처리/반환.
- tx hash, Jetton master, 수신 주소, 수량, 네트워크 비용, 상태, 감사 기록 저장.
- 외부 거래소에 대한 직접 원화 지급·환전 약속 금지.

### 4단계: 공식 역환전 차단 및 P2P 양방향 허용
- 공식 API: TL→TLC만 허용하고 회사의 TLC→TL 발행·환매는 거부한다.
- P2P 주문장: 이용자끼리 기존 TL과 TLC를 양방향 교환할 수 있다. 회사는 양측 자산을 확보하고 에스크로 수수료를 받는다.
- TLC는 TON Jetton 온체인 확정 검증, TL은 V5 원장 잠금·이전. 온체인과 D1은 원자적 처리 불가하므로 정산 상태 머신·복구·분쟁 처리가 필수다.
- 원장 불변식: P2P 체결 전후 TL 총발행량 불변, TLC 총발행량 불변(가스·수수료는 별도 회계), 회사 신규 TL 발행 0.
- 전환 적격·현금 환전 가능 TL과 비적격 TL_A/TL_B의 구분은 P2P 후에도 유지되며 거래로 자격 세탁 불가.

## 2026-10-23 TLC 채굴 공식 재설계 감사 결과
현재 `src/economics.ts`의 `/calc-poc`는 POC = clamp(10 × (0.35 content + 0.25 spend + 0.18 listen + 0.10 upload + 0.12 score), 0.1, 5)로 계산하고, `/mine-tlc`는 월 TL_P 소비액 × 0.08 × POC × 플랜 배율 / 30을 일일 발행 상한으로 사용한다. 기존 공식은 새 TL_A/TL_B 보상 전환 정책과 별개이므로 그대로 병행하면 같은 기여에 대한 중복 발행 위험이 있다.

### 확인된 결함 및 수정 요구
- `/mine-tlc`는 클라이언트가 보낸 `tlc_amount`를 사용한다. 서버가 유효 기여 이벤트와 보상 전환 기록을 직접 검증하고 지급액을 계산하도록 변경한다.
- `users.tlc_balance` 증가와 `tlc_mining_v2` 기록이 별도 DB 요청이며 동시 호출의 중복 채굴 방지가 원자적이지 않다. 원장 트랜잭션 + 유니크 이벤트 키 + 원자적 차감/발행으로 수정한다.
- `/calc-poc`는 로그 삽입 직후 `monthly_tl_p + tl_p_spent`, `total_seconds + seconds`를 사용하므로 같은 요청이 이중 합산될 여지가 있다. 실적 집계는 승인된 이벤트 원장에서 한 번만 한다.
- V5 재생 중도 종료 시 `wallet_bonus`로 돌려주는 금액은 **환불/잔액 반환**이지 신규 기여 보상이 아니다. TLC 전환 적격 TL_B와 반환 TL_B를 반드시 세부 출처로 분리한다.
- 기존 `poc_logs` 및 `users.tlc_balance`와 V5 경제원장 사이 데이터 동기화가 확인되지 않았으므로 과거 TLC 재발행 또는 자동 소각 금지.

### V5 새 공식(정책 설계안, 수치 미확정)
1. `eligible_event_points(user,period)=Σ(verified_event_units × admin_weight × anti_abuse_factor)`; 각 이벤트는 단일 고유 ID와 보상 출처를 가진다.
2. `eligible_reward_atoms = earned_TL_A_atoms + earned_TL_B_atoms - already_converted_atoms - ineligible_refund_atoms`; 잔액 총액이 아니라 보상 원천 로트별 미전환분만 인정한다. 실제 차감은 보상 로트와 잔액 양쪽에서 원자적으로 일치해야 한다.
3. `conversion_rate = admin_base_rate × poc_eligibility_factor`; POC는 **별도 TLC 발행량을 중복 생성하지 않고** 검증·자격·전환 한도에 반영한다.
4. `mintable_TLC = min(floor(eligible_reward_atoms × conversion_rate), user_period_remaining, global_period_remaining, emission_supply_remaining)`. 자산 정밀도는 승인된 TLC Jetton decimals 및 V5 원장 정수 단위에 맞춘다.
5. `TLC issued`와 `TL_A/TL_B burned_or_reserved`를 동일한 전환 이벤트에 연결하며, 중복 청구 시 동일 결과를 재현한다. 실제 온체인 발행/출금은 별도 확정 상태 머신을 거친다.
6. 운영 초기 관리자 수동 설정: 활동별 가중치, 검증 임계값, POC 계수, 전환율, 사용자·전체 발행 한도, 정지 스위치, 정책 버전, 변경 감사 로그. 값 미확정 시 발행 비활성.
7. 기존 TLC 채굴 잔액은 스냅샷 및 정합성 확인 후 별도 레거시 자산으로 보호한다. 마이그레이션은 사용자 권리를 변경하지 않는 승인된 절차로만 수행한다.

### 필수 테스트
- 동일 광고·청취·댓글 이벤트 중복 보고, 병렬 전환 10건, 전환 후 재시도, 취소·반환, TL_P 기원 TL_B 반환, POC 변경, 정책 버전 변경, 월경계, 채굴 한도, D1 부분 실패, 온체인 전송 재시도.
- `issued_TLC <= configured_global_budget`; 동일 이벤트에서 중복 TLC 발행 0; 환불 TL_B의 TLC 전환 0; 발행 전후 V5 TL 원장 대차 합계 0.

## 최종 정책 우선순위 (2026-10-23)
**TL → TLC 단방향은 회사의 공식 발행/환전 정책에만 적용한다. 이용자 간 P2P TLC ↔ TL 교환은 양방향 허용한다.** TL_P 전환 적격 여부는 별도 결정 전까지 미정이다. P2P 체결은 기존 잔액 이전이며 신규 TL 발행이나 회사 역환매가 아니다.
